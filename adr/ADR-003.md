# Architecture Decision Record (ADR-003)
## Adoption of Semantic Design Tokens over Hardcoded Utilities

### Status
**Approved**

### Context & Problem Statement
Ocean's "silent luxury" brand requires precise visual consistency across five distinct user portals (Buyer, Seller, Warehouse, Delivery, Admin). Traditional development relies on hardcoded Tailwind utility classes (e.g., `text-zinc-800`, `bg-zinc-50`), which disperses visual decisions throughout the codebase. If the design team decides to shift the background tint or line thickness, developers must modify hundreds of component files. We need a centralized token hierarchy to maintain structural styling rules.

### Decision Drivers
1. **Figma-to-Code Parity:** Designers build layouts using Figma Variables. The codebase should mirror this naming convention 1-to-1.
2. **Maintenance Velocity:** Global design adjustments (colors, border radii, shadow levels) must resolve from a single configuration file.
3. **Accessibility (WCAG AA):** Tokens must ensure high contrast ratios by default across all viewport sizes.

### Considered Options
* **Option A: Standard Hardcoded Tailwind Classes** (Write classes like `text-gray-900 border-gray-200` directly inside React elements)
* **Option B: Core Structural Tokens** (Map colors directly: `--color-zinc-900`, `--color-zinc-100`)
* **Option C: Semantic Functional Tokens** (Map components to purpose: `--color-text-primary`, `--color-surface-secondary`, `--radius-md`)

---

### Pros and Cons of Options

#### Option A: Hardcoded Tailwind Classes
* **Pros:** Standard development workflow, no custom config setups required.
* **Cons:** High coupling to specific color scales. Zero alignment with design files. Renaming or tweaking a brand accent becomes a multi-file refactoring challenge.

#### Option B: Core Structural Tokens
* **Pros:** Centralizes standard values.
* **Cons:** Fails to convey context. If `--color-zinc-200` is used for both borders and disabled buttons, changing the border color will unintentionally alter button layouts.

#### Option C: Semantic Functional Tokens
* **Pros:** Provides semantic context (e.g., `surface-primary` for panels, `text-muted` for sub-labels, `border-focus` for active outlines).
* **Pros:** Separates the *value* of the token from its *intent*. We can change the actual hex code of `surface-secondary` in one central JSON file without breaking the intent of any layout.
* **Pros:** Seamless matching with Figma variables and Storybook schemas, allowing automatic synchronization.
* **Cons:** Requires initial configuration effort to structure the `/docs/29-tokens.json` file and declare them inside Tailwind configs.

---

### Decision Outcome
We selected **Option C: Semantic Functional Tokens**.

We compiled our tokens inside `/docs/29-tokens.json` and linked them to our global stylesheet (`src/index.css`) and Tailwind definitions. This guarantees that designers and engineers communicate using the exact same vocabulary.

#### Consequences
* **Clean Code:** Standard UI cards are styled with semantic classes like `bg-surface-primary text-text-primary border-border-default` instead of rigid hex references.
* **Synchronized Systems:** Figma variables, JSON tokens, React components, and Storybook specs are aligned 1-to-1, eliminating design drifts.
