# Architecture Decision Record (ADR-001)
## Choice of Core Database: PostgreSQL vs. MongoDB

### Status
**Approved**

### Context & Problem Statement
Ocean is a multi-vendor marketplace supporting distinct buyer, seller, warehouse, and delivery portals. The system requires complex transactional flows, strict stock level concurrency, multi-table financial records (order tables, line-items, and connected escrow balances), and complex relational queries. We need a persistent storage system that satisfies both highly reliable ACID compliance and high-performance querying under concurrent loads.

### Decision Drivers
1. **Strict Financial Integrity:** Financial settlements, connected seller accounts, and escrow freezes demand atomic transactions (ACID).
2. **Concurrency & Inventory Management:** Simultaneous checkouts for the same SKU require row-level database locking (e.g., `SELECT FOR UPDATE`) to prevent overselling.
3. **Complex Relational Queries:** Connecting listings, user profiles, orders, and review metadata requires high-performance SQL JOIN operations.
4. **Semantic Extensions:** Support for dense vector embeddings (specifically 768-dimensional vectors from Gemini's `text-embedding-004` model) inside the same database engine without spinning up standalone cluster infrastructures.

### Considered Options
* **Option A: MongoDB (Document Store)**
* **Option B: PostgreSQL (Relational Database)**

---

### Pros and Cons of Options

#### Option A: MongoDB
* **Pros:** Highly dynamic schemas, fast single-document write performance, horizontal partitioning (sharding) out of the box.
* **Cons:** Weak or overly complex support for multi-document ACID transactions across distributed shards. Joining collections is slow and expensive. No native, optimized support for transactional relational locking of items in stock grids.

#### Option B: PostgreSQL
* **Pros:** Complete, enterprise-grade SQL compliance, rigid schemas with strict foreign key cascading constraints, advanced transaction isolation levels, native row locking (`FOR UPDATE`), and support for high-performance indexing.
* **Pros (Bonus):** Excellent ecosystem support for `pgvector`, allowing us to store high-dimensional dense vectors directly in the same tables as product catalogs, enabling high-performance semantic search without external database synchronizations.
* **Cons:** Schema migrations require careful planning and lock management under heavy active traffic.

---

### Decision Outcome
We selected **Option B: PostgreSQL**. 

PostgreSQL matches our core structural domain perfectly: transactions are critical, integrity cannot be compromised, and catalog entries are highly structured. The presence of **`pgvector`** allowed us to combine transactional SQL metadata with our semantic vector search pipelines in a single unified storage engine.

#### Consequences
* **Consistency:** All financial logs and inventory balances enjoy strict transactions.
* **Validation:** Out-of-stock items can be identified and locked during checkout inside a single atomic operation.
* **Simplicity:** No need to synchronize PostgreSQL and a standalone Vector Database (like Pinecone), drastically reducing operational infrastructure complexity.
