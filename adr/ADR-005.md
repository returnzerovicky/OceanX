# Architecture Decision Record (ADR-005)
## Event-Driven Architecture for Order Processing

### Status
**Approved**

### Context & Problem Statement
When a customer submits an order on Ocean, the checkout system must coordinate multiple operations:
1. Deduct stock levels in inventory tables.
2. Generate packing slips for sellers.
3. Call shipping APIs to generate tracking labels.
4. Compose and dispatch HTML invoice emails.
5. Log transaction metrics for sales analysis.
6. Recompute the user's category affinity vectors.

Executing all of these tasks inside a single synchronous API call makes the request fragile and slow. If the email API times out or the shipping platform is down, the entire transaction would crash, blocking the purchase. We need a system that decouples these responsibilities.

### Decision Drivers
1. **Fault Isolation:** Failure in non-critical systems (like emails or analytics logging) must never block critical checkout success.
2. **Transaction Latency:** The synchronous checkout path must complete in under 150ms to provide rapid user checkout.
3. **Horizontal Scalability:** Heavy background tasks (like generating labels or recalculating affinities) should execute independently without blocking server resources.

### Considered Options
* **Option A: Monolithic Synchronous Chain** (Execute all actions in a single, blocking controller function)
* **Option B: Asynchronous Promise.all()** (Spawn promises inside Express and return 200 without waiting)
* **Option C: Event-Driven Message Distribution** (Publish an `order.completed` event to an in-memory or external Event Bus)

---

### Pros and Cons of Options

#### Option A: Monolithic Synchronous Chain
* **Pros:** Extremely simple to write and debug. Easy transactional rollbacks if something fails.
* **Cons:** Fragile. Total response time is the sum of all third-party API latencies, which regularly exceeds 1.5 seconds. If any step fails, the customer faces confusing checkout errors.

#### Option B: Asynchronous Promise.all()
* **Pros:** Non-blocking, faster response times.
* **Cons:** Poor reliability. If the Node process crashes or restarts (due to autoscaling or redeployment) while background promises are unresolved, those tasks are lost forever. No structural retry queues.

#### Option C: Event-Driven Message Distribution
* **Pros:** Clean architectural separation. The Express endpoint only writes to the DB, publishes an event, and returns 200 OK instantly.
* **Pros:** Fault isolation. If the notification service fails, the order is still safely completed. The subscriber can retry the email delivery when the service recovers.
* **Pros:** Horizontal scalability. Services can be scaled independently depending on processing load.
* **Cons:** Eventual consistency. Systems are synchronized asynchronously, requiring a solid error tracking strategy.

---

### Decision Outcome
We selected **Option C: Event-Driven Message Distribution**.

Our core Express server acts as a message publisher, dispatching `order.completed` events immediately upon a successful Stripe payment. Independent subscribers process specialized business rules asynchronously.

#### Consequences
* **Decoupled Architecture:** The system remains resilient, and checking out is extremely fast.
* **Resilience:** If the courier label service goes offline, shipping slips are queued and retried automatically. The buyer's experience remains unaffected.
