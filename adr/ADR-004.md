# Architecture Decision Record (ADR-004)
## Implementation of Optimistic UI Updates for Core Client Interactivity

### Status
**Approved**

### Context & Problem Statement
Ocean targets an Interaction to Next Paint (INP) metric of **under 100ms** to provide a fast shopping experience. Traditional web architectures follow a Pessimistic pattern: when a user clicks "Add to Bag", toggles a wishlist item, or deletes an item, the client displays a loader and waits for the database write to succeed before updating the interface. Under slow mobile connections, this creates noticeable lag, leading users to believe the app is unresponsive. We need a strategy to make operations feel instant.

### Decision Drivers
1. **Interactive Performance:** UI updates must paint within 100ms of user input, regardless of cellular network latency.
2. **State Syncing Reliability:** Client and server states must remain consistent. If a server-side write fails, the UI must revert to previous states gracefully.
3. **Bandwidth Efficiency:** Avoid excessive layout recalculations (CLS) and screen flickering during rapid interactions.

### Considered Options
* **Option A: Pessimistic State Model** (Await API response -> render spinners -> paint updated state)
* **Option B: Skeletal Waiting Model** (Paint a placeholder skeleton immediately -> swap with real data on API finish)
* **Option C: Optimistic State Model** (Update client state instantly assuming success -> dispatch API -> revert on error)

---

### Pros and Cons of Options

#### Option A: Pessimistic State Model
* **Pros:** Bulletproof state accuracy. The UI never displays data that doesn't exist on the server.
* **Cons:** Frustrating user experience. Adding a product to a cart displays an active delay, slowing down customer flow and lowering overall conversion rates.

#### Option B: Skeletal Waiting Model
* **Pros:** Prevents layout shifting (CLS) during load sequences.
* **Cons:** Still introduces cognitive latency. Spinning wheels or skeletons distract from the natural flow of shopping.

#### Option C: Optimistic State Model
* **Pros:** Instant feedback. The item count in the header increases within milliseconds of tapping "Add to Bag", producing a tactile, mechanical feel.
* **Pros:** Satisfies Ocean's INP target (<100ms) with ease.
* **Cons:** Requires a robust rollback mechanism. If the API returns a rate limit or inventory conflict, the state must transition back to its previous value and display an inline warning banner.

---

### Decision Outcome
We selected **Option C: Optimistic State Model** for three core workflows:
1. **Shopping Bag Modifications:** Adding/removing items or editing quantities.
2. **Wishlist Toggles:** Adding products to favorites.
3. **Review Rating Logs:** Submitting or helpful-voting reviews.

#### Consequences
* **State Management:** React components store the previous state before updating. The API call is wrapped in a standard `try-catch` block: if a non-200 code is received, the cached previous state is restored, and an error notification is fired.
* **Client Performance:** Taps and selections feel incredibly responsive, resulting in higher user engagement scores.
